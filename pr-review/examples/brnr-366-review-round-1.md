1. issue (non-blocking) — `src/host/acp.rs:715` (with `src/host/approvals.rs:405`) — For a cancel after the session's close, `give_up` first calls `keep(...)` on the entry, and only after that `agent_cancel` calls `self.approvals.closed(s)` to remove it again. When `given_up` already holds `GIVEN_UP` entries, `keep` pops the oldest entry (a request whose session is still open), and then `closed` removes the new one. The result is one valid entry lost for no reason. After that, the editor's answer to that request is recorded in the host log, not in its session's transcript. Also, `closed(s)` sweeps `answered` too. Today that has no effect: control answers need an open session (`session_index`), and with an editor the timers do not fire. But the call says more than "do not keep this one". This can wait because it occurs only at the cap and costs only where one answer is recorded. Fix: decide before you keep the entry. For example, give `give_up` a flag that says whether the session is open (or check `find` in `agent_cancel` before the call), so a closed session's cancel never enters `given_up`. Then the cap evicts only when it must.
2. suggestion (non-blocking) — `src/host/sessions.rs:635` — The new test calls `approvals.editor_answer` directly, so it shows what the map holds, not what the editor and the agent see. Its sibling `adr_0010_a_closed_sessions_answered_requests_go` (`sessions.rs:588-610`) sends the editor's answer with `h.editor_bytes` and asserts on `h.sent().agent`. If you follow that pattern here, the test also proves the claim this PR adds to ADR 10.3: the editor's answer to a cancelled request that is no longer kept "still goes to the agent as it is". The rule (AGENTS.md, "Writing code here") asks for a test that shows the behaviour change, and a test through the harness shows it from the outside. Fix: send `{"id":7,"result":{...}}` with `h.editor_bytes` and assert that `h.sent().agent` has it in both cases.
